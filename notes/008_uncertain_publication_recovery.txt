Uncertain publication: core correctness and recovery policy
==========================================================

Date: 2026-11-14
Status: historical selected strict-observation implementation in sections
9-10; revised continuation-first Tier-1 plan in section 11 (not implemented).
Inspected baseline: main@a935eba5f2d3c91e807094a7cfc7d5cc74bc5e27.

Note 000 governs concrete delegation and protected-core changes. Note 004
owns Tier-0 correctness and qualification; Note 007 records Tier-1 evidence.
Sections 1-8 preserve the original design analysis; sections 9-10 record the
implemented and qualified journal-owned observation contract. Section 11

The default CLI still fails fast. No production activation is authorized.

1. Decision and ownership
-------------------------

Tier 0 establishes durable facts and performs all authoritative indexing.
Tier 1 decides whether and when to invoke that same implementation again.
An uncertain publication must not lead to a second journal-consistency
algorithm in Tier 1, even if that algorithm only reads PostgreSQL.

First establish that the original application can continue safely from
retained history after an uncertain publication, without the previous
writer's memory. Add attempt-specific verification only if a concrete
recovery requirement cannot be met by that existing restart path.
Moving an unnecessary comparison into Tier 0 would not make it necessary.

Preserve one scanner, one complete-block publisher, one checked repair,
one checkpoint-bound reader and one ordinary catch-up/tip-following loop.
No transaction replay, publication registry, new table, digest ledger,
secondary HTTP decoder or alternative application loop is proposed.

2. Two different questions
--------------------------

Continuation:
  Can a fresh exclusive writer continue from the durable journal through
  the original source admission, chain checks and publication operation?

Attempt-specific observation:
  Does durable storage contain precisely the expected effect of a given
  publication, or precisely its unchanged original basis?

The first is essential restart correctness. The second is a stronger,
optional observation. An expected effect being present does not prove which
invocation produced it. The proposed attempt context would not provide a
unique durable transaction identity or exactly-once invocation semantics.

A process crash can erase all attempt context. Ordinary Tier-0 restart must
still work within its qualified storage and source assumptions. It cannot
then report an attempt-specific result, nor does restart retroactively turn
an unanswered invocation into a confirmed success.

3. What the current implementation establishes
----------------------------------------------

src/conix/journal.py:
  Journal.publish_block stores the block, selected raw events and updated
  progress in one transaction. _advance_progress fences the original
  source, generation, revision, checkpoint and blocked state.
  _transaction retires the journal on loss of COMMIT confirmation. It raises
  CommitOutcomeUnknown for ordinary exceptions; cancellation propagates.
  The same transaction helper also serves Journal.repair_to.

  Journal.open verifies the database role, acquires the exclusive writer
  advisory lock, then checks source identity and reads progress and its tip.
  It admits blocked history for inspection; opening does not authorize
  publication or prove that every retained event has been revalidated.

src/conix/core.py and src/conix/app.py:
  open_writer adds RPC source admission. Writer.advance_one checks the
  retained tip against fresh chain evidence, acquires and validates the
  next complete block, then calls the original Journal.publish_block.
  app.run owns the ordinary catch-up and tip-following loop and propagates
  failures. It contains no automatic uncertain-COMMIT recovery policy.

Existing tests provide narrower evidence than the proposed end-to-end gate:
  tests/test_journal.py, check_unconfirmed_publication, covers an injected
  failure before COMMIT is sent and a real server COMMIT with its reply
  dropped. It checks reopened progress, candidate rows and duplicate
  publication refusal. tests/pg_commit_reply.py owns the lost-reply fixture.
  tests/test_t1_database.py checks that an actual lost COMMIT reply does not
  restart T1-D1 and that the one committed block remains in PostgreSQL.
  tests/test_t0_7e_faults.py includes an installed-CLI lost-COMMIT-reply test
  followed by explicit process restart, fresh RPC verification and one
  retained Transfer event. Note 004 section 11.5.1 records that evidence.

Those tests support atomic storage, retirement and explicit process restart.
The installed-CLI test accepts either stored checkpoint before restart and
targets the attempted height; it does not force both outcomes or require a
new publication beyond an already committed tip. Extend that witness rather
than claim ordinary restart has no evidence. None of these tests qualifies
the proposed T1-D2 policy. Existing revision-bound results remain in Notes
004 and 007; this source inspection is not a new test run.

4. Required Tier-0 continuation contract
----------------------------------------

After an uncertain publication, retire the old application session and
abandon its writer and prepared inputs. A new original application opens
its own writer, reacquires exclusive ownership and reads the durable basis.
It performs all ordinary source and chain checks before advancing.

If the transaction did not commit, the next original advance reacquires
and validates the candidate block. If it committed, the next advance starts
after the stored checkpoint. Neither path resubmits the abandoned SQL
transaction or treats its previously acquired RPC evidence as current.

This contract assumes the existing atomic journal and supported ownership
model. It is not a full database corruption audit, protection from an owner
bypassing the writer protocol, or proof of chain finality. A changed source,
blocked history, missing evidence or contradictory chain still fails at its
original owner. Recovery does not waive those checks or clear an operator
hold. Reorganization remains subject to the existing checked repair path.

Local retirement and fresh database ownership are separate obligations:
  - The previous application must have exited its resource lifetimes.
  - The new session must actually acquire the database writer lock.
  - Failed or unconfirmed cleanup does not grant a restart.
  - WriterBusy does not establish either publication outcome.
Cancellation and a requested stop prohibit another automatic session.
The journal's retired flag means the object is unusable, not that cleanup
succeeded. Today _transaction suppresses its first close failure and the
owning open_journal context attempts close again. Qualification must observe
actual lifetime completion and fresh ownership, not just that flag.

5. Minimal T1-D2 policy, subject to qualification
------------------------------------------------

The current CommitOutcomeUnknown does not distinguish publication from
repair. Catching it indiscriminately would broaden recovery to uncertain
repair. Before any automatic publication recovery, Tier 0 must provide a
reliable operation distinction at the actual failure boundary. Tier 1 must
not infer it from exception text, a traceback or its last observed callback.
The representation is an implementation decision; full block/event context
is not required merely to identify the operation.

The proposed sequence is:
  original application reports publication COMMIT uncertainty
    -> complete old-session retirement
    -> check cancellation, stop and the bounded recovery budget
    -> invoke the original application with a fresh writer
    -> original admission and advance determine whether it can proceed.

This is a proposal to permit continuation while the previous invocation's
outcome remains unknown. It is not a claim that uncertainty was reconciled.
If the desired policy requires that particular effect to be established
first, select the optional contract in section 6 instead.

If stop arrives between the policy check and fresh application entry and
prevents resumed work, preserve the original publication uncertainty; an
immediate return from app.run must not turn it into recovery success.
Cancellation still propagates. After resumption, normal stop follows the
existing lifecycle, but a clean application return is never confirmation
of the previous invocation's publication outcome.

Before implementing this policy, specify a finite restart budget, bounded
waits and their interaction with existing T1-B/C/D1 budgets. Re-entering a
nested supervisor must not reset the D2 budget and allow unlimited recovery.
No generic SQL retry or uncertain-repair recovery is admitted. T1-D1's
SQLSTATE-free disconnection exclusion remains intact: absence of SQLSTATE
alone never grants restart. D2 instead requires the core's publication-COMMIT
provenance, retirement and bounded policy, even if the lost reply has no
SQLSTATE. Cancellation at COMMIT can surface through app.run's timeout as
TimeoutError; generic timeouts do not identify publication uncertainty.
An unclassified uncertainty remains an error. A failure during fresh
admission does not become permission to bypass admission.

6. Optional core-owned expected-effect verification
---------------------------------------------------

Decision gate: identify a consumer or recovery rule that requires exact
attempt-specific observation beyond safe continuation. If none exists,
omit this capability. The following describes its contract, not a committed
API name, implementation plan or prerequisite for every process restart.

If needed, Journal.publish_block constructs immutable attempt context from
its original Progress, proposed Block and exact RawEvent tuple.
The context accompanies publication uncertainty only. Tier 1 neither
reconstructs it nor maintains a parallel publication identity. It remains
bounded by the existing admitted block/event limits and is not serialized
into diagnostics, logs or another durable ledger.

A journal-owned reconciliation operation observes storage under a fresh
exclusive journal session after old-session retirement. It performs no
publication, repair, unblock or transaction replay. It must verify the
selected source and compare one consistent durable observation:

  ORIGINAL_BASIS_PRESERVED
    The complete original Progress is unchanged, and the candidate block
    and its event rows are absent.

  EXPECTED_EFFECT_PRESENT
    Source, generation and history start match the attempt; revision is
    exactly original revision + 1; the checkpoint is the exact proposed
    block; the blocked state is the expected unblocked state. Every stored
    block field and event field matches, with no missing or extra events.
    Match events by their stored (block_number, log_index) identity and all
    payload fields; incidental SQL row order does not establish equality.

  OTHER_DURABLE_STATE
    The read completed, but a changed generation, unexpected revision,
    different block/event set or operator hold establishes neither expected
    state. A later valid advance is outside this narrow comparison too.
    This observation refuses the stricter recovery rule; it does not by
    itself establish corruption, unsafe ordinary restart or a failed read.

These labels express distinct meanings, not a requirement for an enum or
three independent flags. Choose the smallest representation the caller needs.

Observe progress and candidate rows coherently under the existing exclusive
ownership contract. Choose the read strategy explicitly; do not add a
durable write transaction, schema or reconciliation ledger. If a read
transaction is needed, it belongs to the observation. Neither that snapshot
nor the advisory lock promises safety against arbitrary owner mutations
outside the supported ownership model.

Failure to obtain a consistent observation is separate from observing another
durable state. Preserve causes for invalid evidence, unavailable storage,
interruption and failed retirement. An opaque UNRESOLVED result must not
erase the actual cause or phase. None authorizes continuation by this
stricter policy. Report bounded source-controlled facts; do not print attempt
payloads, driver messages, credentials or untrusted exception prose.

Either matching observation settles only this comparison. It is not a
reusable permission token: release the inspection session, then restart the
original application, which reacquires ownership and rechecks all admission
and chain evidence. A concurrent change after inspection is handled by those
ordinary checks. An uncertain repair remains outside this capability.

7. Proof and implementation gates
----------------------------------

First extend the existing contained PostgreSQL/Anvil witnesses, including the
installed-CLI explicit restart test. Force each outcome: an unsent COMMIT and
a committed transaction with a dropped reply. Require subsequent publication
beyond the recovered checkpoint through original app.run/open_writer,
Writer.advance_one and Journal.publish_block, fresh RPC evidence, correct
durable progress and public-reader history without duplicate events.
Discard previous attempt memory. Include an empty block and a selected-event
block, and stop the application through its ordinary cancellation/lifecycle.

Negative cases must show that contention, wrong source, blocked history,
missing/contradictory evidence, failed retirement, stop and cancellation do
not bypass the existing guards. Preserve and extend the real process-restart
witness so continuation cannot rely on a caught Python exception. Reuse the
maintained fixtures and lanes rather than create another harness.

Only after that proof, choose continuation-only policy or the stricter
expected-effect gate. If the latter is needed, add real PostgreSQL tests for
both matching observations, changed generation/revision/source, altered or
missing/extra event rows, unavailable storage, interrupted reads and repair
uncertainty exclusion. Check that inspection itself leaves history unchanged.

Qualify T1-D2 separately: concrete delegation, reliable publication provenance,
finite recovery across nested supervisors, cancellation, and no restart after
retirement failure. Exercise stop arriving between the recovery gate and
fresh application entry; no resumed work means no reported recovery success.
If the stricter policy is selected, also prove refusal on other durable
states or failed verification. Inspect final history through the public
reader. Successful output alone is not proof of delegation.

Use behavioral RED -> GREEN for necessary implementation changes. Run the
maintained CI steps locally on the selected rootless Engine and explicit
shared wheelhouse. Record exact revisions and limits in Note 007; hosted CI
is supplementary. Contained tests do not imply retained-service, dapp32 or
production qualification. No new qualification is claimed by this note.

8. Protected-core change discipline
------------------------------------

Note 000's zero feature-driven protected-operation edit target remains in
force. An added public method does not exempt changes to publish_block or
_transaction from review. Attempt capture would change a protected operation
even with identical SQL; do not call the core literally unchanged.

If existing restart correctness fails, correct the defect in its original
Tier-0 owner and demonstrate the failing behavior. If operation provenance
or expected-effect verification requires a new core contract, explicitly
review and record that shared-design extension against Note 000 before
implementation. T1 convenience alone is not a correctness defect or a reason
to add unused flexibility. No protected-core exception is granted here.

Current disposition: prove restart correctness first; decide the smallest
required core contract next; then implement bounded opt-in T1 policy. Keep
attempt-specific verification conditional. Keep every authoritative storage
comparison and mutation in the original journal.


9. Selected implementation contract (2026-11-14)
------------------------------------------------

The implementation selects the stricter expected-effect gate for T1-D2.
Its purpose is to permit bounded automatic continuation only after the
original journal has established one of the two matching observations.
Ordinary manual/process restart remains independent of attempt memory.

Tier 0 adds immutable PublicationAttempt context and a publication-specific
subclass of CommitOutcomeUnknown. The original publish_block captures the
original basis and exact candidate inputs; repair uncertainty retains the
existing base exception. The journal compares a fresh read-only snapshot
under its exclusive writer session, returning original basis preserved,
expected effect present, or another durable state. Storage failures and
cancellation remain exceptions. Observation makes no durable changes.

The original app.run gains the narrow optional writer-session composition
argument already used on tier-1; its default still opens the original writer.
This explicitly approves that shared contract and the journal additions
against Note 000's protected-core change rule. Publication SQL, complete-block
validation, schema, checked repair and the ordinary loop retain their owners
and algorithms. This approval does not authorize broader core flexibility.

Tier 1 adds an opt-in wrapper around the existing database/reorg/read
composition. It admits only publication-specific uncertainty, retires the
previous invocation, then opens the original journal to compare its attempt.
Only a matching result followed by successful inspection-session retirement
permits another original application invocation. It allows at most two such
recoveries with cancellable 100/200 ms waits; this outer budget is never reset
by nested supervisors. Other states, unavailable evidence, stop, cancellation,
unknown repair outcome and cleanup failures stop automatic recovery.

A stop that prevents fresh application entry preserves the original failure.
A clean later shutdown does not confirm the identity of the invocation that
produced the formerly uncertain effect. No default CLI recovery is enabled.

First prove and implement these capabilities on tier-0, then merge that core
into tier-1 and qualify the wrapper. Main remains stable and unchanged until
a separate promotion decision. Earlier conditional discussion explains the
design choice; this section selects it without claiming test results.

The original application also returns a closed RunOutcome distinguishing
a stopped invocation that never entered an advance from one that did. Nested
Tier-1 supervisors forward this result; D2 must not treat a pre-entry stop as
successful resumption. This reports execution, not publication attribution.

11. Revised Tier-1 plan — continuation first (2026-11-14)
----------------------------------------------------------

Decision: prioritize reliable service resumption after publication-specific
COMMIT uncertainty. The strict journal observation from sections 9-10 is a
supported Tier-0 inspection capability, but must NOT be a mandatory gateway
for normal Tier-1 recovery. This reverses only the Tier-1 policy selection
in section 9; the implementation and its qualification records remain
historically accurate until the proposed change is made.

Why: the durable journal may legitimately move beyond the exact originally
attempted revision after the failed writer retires. For example, another
authorized original writer can advance the checkpoint before D2 examines
the attempt. The current strict reconcile_publication() correctly returns
OTHER_DURABLE_STATE in that situation, but that is not evidence of corruption
or an unsafe ordinary restart. Treating this non-match as a terminal
recovery decision creates avoidable downtime. The same applies when an
additional diagnostic observation is unavailable yet normal fresh writer
admission would succeed.

Selected execution contract:
  Original Tier-0 publish_block loses its COMMIT acknowledgment
    -> emits journal-originated PublicationOutcomeUnknown
    -> the entire original application/writer/HTTP session retires
    -> Tier-1 applies its existing bounded, cancellable recovery delay
    -> invoke the SAME existing D1/C/B/A -> Tier-0 app.run composition
    -> original core.open_writer re-acquires writer exclusion and source
       admission and inspects the authoritative durable checkpoint
    -> original Writer.advance_one rechecks current chain evidence and
       proceeds through original Journal.publish_block.

No replay of the abandoned SQL operation, reuse of the previous writer,
reuse of earlier RPC evidence, second journal validator, alternate scan
loop, shadow checkpoint or new database table. The fresh original
application determines what work is needed; recovery never claims to know
which invocation committed the earlier transaction.

Tier-0 contract:
  Keep PublicationAttempt, PublicationOutcomeUnknown, and
  Journal.reconcile_publication as already implemented and independently
  testable. They remain useful for an explicit request for attempt-specific
  observation, not a prerequisite to resuming normal service. Preserve
  Journal._transaction, atomic publication and progress fencing, checked
  repair, the original loop, and the narrow RunOutcome session seam.
  No new Tier-0 source modification is proposed for this policy change.

Tier-1 delta:
  Modify only the opt-in
  conix.resilience.publication.supervise_with_publication_recovery policy.
  Catch only the original journal's PublicationOutcomeUnknown, after the
  failed application has exited all resource lifetimes. Do not invoke
  open_journal/reconcile_publication as a continuation gate; do not add
  replacement SQL inspection, new error classes or diagnostic persistence.
  Invoke the original existing supervised application afresh. Continue to
  propagate its source/chain/history/operator-hold failures unchanged.
  An uncertain repair-to-COMMIT stays outside publication recovery.
  Preserve the T1-D1 wrong-password/SQLSTATE-free exclusion; do not
  broaden generic SQL or timeout classification.

Pacing and stop:
  Retain the existing local D2 recovery delay and finite retry policy.
  Do NOT add a global total-session cap across D2/D1/C/B: that would
  introduce another terminal condition without demonstrating an
  operational problem. Existing nested limits can multiply; document the
  actual bound rather than pretend they share one budget. If measured
  repeated transient failures require change later, improve pacing or
  the external service lifecycle separately rather than impose another
  arbitrary failure gate.
  A requested stop, task cancellation or unconfirmed retirement remains
  authoritative. A stop before a resumed advance enters must not turn
  the previous uncertain result into reported recovery success. Preserve
  RunOutcome propagation but do not interpret entering an advance as
  confirmation that the earlier COMMIT succeeded.

Test-first behavioral revision on the maintained tier-1 branch:
  1. Demonstrate RED using the existing original Anvil/PostgreSQL fixture:
     after a real lost-COMMIT reply, allow a separate legitimately
     authorized original writer to advance the durable checkpoint before
     D2 continuation. The current mandatory strict snapshot returns
     OTHER_DURABLE_STATE and stops. Require resumed original app.run to
     continue successfully, with source/generation integrity, Reader
     visibility and no duplicate events. Distinguish this from an
     unauthorized out-of-band mutation.
  2. GREEN by removing only the mandatory observation call from the
     normal D2 supervisor, retaining original publication provenance,
     previous-session retirement, RunOutcome and existing bounded
     stop-aware retry behavior. No alternate SQL recovery algorithm.
  3. Re-exercise both actual COMMIT outcomes (unsent COMMIT and server
     COMMIT with dropped reply), ordinary restart without attempt memory,
     fresh selected RPC verification, the next empty block and a selected
     emitted event. Assert original Journal.publish_block delegation and
     unique Reader events. A healthy journal must not be made unavailable
     merely because optional strict inspection cannot match or cannot run.
  4. Preserve negative controls: unknown repair outcome, wrong password,
     wrong source, blocked history, actual journal source/chain conflict,
     failed writer cleanup, stop, cancellation, and false-success on a
     pre-entry stop. These are existing core correctness boundaries, not
     new policy-imposed failure cases. Do not weaken their tests to make
     the continuation scenario pass.
  5. Run full maintained host checks and contained CI on the selected
     fw/rootless agentic Engine; independently review actual delegation,
     cleanup and failure classes. Re-run the retained-service and owned
     dapp32 integration campaigns before promotion to stable main, using
     existing acceptance lanes. Record exact revisions, results and
     limits in Note 007.

Until this plan is implemented and qualified, tier-1@ed3c4fc retains
the strict mandatory observation behavior of section 9. This plan is
not a claim of completion or an instruction to activate the default CLI.
No changes to production deployment or stable main are authorized.
