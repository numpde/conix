Conix — Named Tier-0-7 B deployment operator contract
====================================================
12 November 2026

Purpose and boundary
--------------------
A named deployment selects its Docker Engine, source and borrowed resources
once. One editable file owns all nonsecret selections:

    config/deployments/<name>/deployment.toml

Other paths derive exclusively from that directory:

    config/deployments/<name>/deployment.lock.toml   generated, mode 0600
    config/deployments/<name>/abi/<selected>.json     selected ABI files
    config/deployments/<name>/secrets/runtime.dsn     runtime credential, 0600
    config/deployments/<name>/secrets/owner.dsn       schema-owner credential, 0600

The named directory and abi/ and secrets/ subdirectories are owner-owned
mode 0700. Deployment.toml is owner-only mode 0600. No other editable source
configuration, path-selector settings, redundant lock or host credentials
registry exists. Explicit old per-operation resource/path overrides are
rejected, not ignored. Existing older prepared.json files convey no authority.

Initialization and source configuration
---------------------------------------
  make deployment/config/init DEPLOYMENT=local DOCKER_CONTEXT=agentic

Init requires an explicit named local context. It creates an owner-only
deployment skeleton and both private directories, without trying Docker,
creating credentials, inventing source coordinates, installing database roles,
or selecting network names. After init, edit the one deployment.toml and
supply the selected ABI and DSN files. Init never overwrites existing config.

deployment.toml version 1 requires docker_context, wheelhouse (absolute
directory), database_network, rpc_network (distinct existing local internal
bridges), [chain] (chain_id, genesis_hash, start_block, rpc_url), [contracts.<alias>]
(address, abi_file, selected events), and [limits] (the authoritative Tier 0
limit fields). A selected ABI path has form abi/<name>.json. See
examples/deployment.toml.example for the structure; all chain addresses and
identities in examples are illustrative, NOT selected for the user.

Missing source/resource settings fail before Docker work. Source coordinates
are explicitly provided; no fallback to an example, current RPC head or
ambient database credential is allowed. The saved Docker context is used on
all later named operations, and a conflicting command-line selection fails.

Preparation and generated lock
------------------------------
  make deployment/prepare DEPLOYMENT=local

Prepare owns host composition only. It reads the editable definition and
projects its [chain], [contracts] and [limits] to a temporary plain Tier 0
catalog, adding only [database] with dsn_file=/run/conix/connection.dsn and
runtime_role=conix_runtime. The projection resides only for input staging in
the named directory, adjacent to the selected ABI directory, then is retired.
The installed catalog alone interprets source/event/ABI semantics.

The existing staging protocol copies only the projected catalog, selected
declared ABI members, and runtime.dsn into a private Engine volume. It does
not mount the host deployment directory or read owner.dsn. The wheelhouse
and pinned base images must already be acquired; prepare builds offline
and verifies the exact image and staged installed input snapshot.

Only after successful build, image verification and input staging does
preparation atomically publish deployment.lock.toml (version=1, image=exact
sha256 ID, volume=exact Conix-owned input volume). It writes a private
temporary file, fsyncs it and replaces the lock atomically. A failed build,
image check, staging or pre-publication write preserves the prior lock.
If lock publication fails, the new input volume is retired best effort.
The former prepared.json writer/reader is gone; there is no fallback.
A completed replacement may retire the old input volume, but never an
in-use deployment: preparation refuses an existing service.

Startup and administration
--------------------------
  make deployment/database/schema/init DEPLOYMENT=local
  make deployment/config/check DEPLOYMENT=local
  make deployment/up DEPLOYMENT=local
  make deployment/status DEPLOYMENT=local
  make deployment/logs DEPLOYMENT=local
  make deployment/down DEPLOYMENT=local

Owner schema initialization assumes externally provisioned PostgreSQL and
conix_owner/conix_runtime/conix_reader roles and schema. Its dedicated
initializer reads only secrets/owner.dsn through private stdin to a one-shot
non-root container, never argv, logs, staged runtime inputs or a host mount.
It executes the installed conix.schema.initialize() and is not a migration.
On an unknown result, inspect durable history rather than replaying blindly.

Startup admits only one prepared TOML lock under the same deployment
operator lock as preparation, before Docker client selection. It verifies
the exact image role, private volume ownership and runtime readability,
two selected internal network identities, and the actual stopped container
confinement. No downloads, rebuilds, database initialization, automatic
reorganization repair, or transient RPC retries occur at startup.
The container runs the unchanged variant-B catch-up/tip-following loop.

Status, logs and down use the saved engine and exact project ownership;
they work without the prepared image/lock and do not delete external
networks, PostgreSQL history or the selected input volume. An absent
deployment.toml permits explicit-context recovery for those read/retire
operations only. A corrupt file or broken symlink is not equivalent to
an absent configuration. No deployment is selected by default.

Tests and legacy diagnostics
----------------------------
  make test/repository/run
  make repository/inputs/check
  make test/indexer/run DOCKER_CONTEXT=agentic RUNNER_IMAGE=<verified-test-image>

The contained indexer lane owns a disposable PostgreSQL/Anvil graph, initializes
the owner-only schema and launches the real installed conix run process,
including SIGTERM and durable-tip behavior. It is not retained deployment
qualification. The separately triggered dapp32 campaign qualifies real
token/payment/restart/reorg scenarios on the selected host. The actual
retained-service lifecycle still requires separate verification on a
rootless Engine with explicitly provisioned external inputs.

Low-level history/block/advance, deployment/inputs/stage and deployment/inputs/remove and image/
wheelhouse commands remain explicit diagnostic/build primitives. They are
not alternate normal deployment flows. The public deployment/start and
deployment/remove aliases remain retired.

Make values are captured literally, never interpreted as shell syntax.
Public checks remain fail-closed. Follow the original trusted input
policies; do not add duplicate catalog validation or permit secrets,
Docker sockets or owner credentials in the runtime.

Retained deployment acceptance
-----------------------------
test/deployment/acceptance/run owns the stable deployment-acceptance test identity. Its
complete definition, ABI and disposable DSNs are tracked under
config/deployments/deployment-acceptance/. They are test credentials only;
never install real deployment credentials in that directory. Git cannot
represent the required 0700/0600 private modes, so the lane installs them
before normal deployment admission. The saved context and wheelhouse are the
selection authority; any supplied per-call selectors must agree with them.
The acceptance harness uses only supported, immutable named-deployment
inspections to read selected resource facts and prepared image/volume IDs;
it never imports private deployment/lock readers. The normal Make lifecycle
remains the only activation/retirement path.

The external PG/Anvil fixture is declared in compose/deployment-test.yml,
using the existing reviewed test services, two owned internal bridges and no
host ports. Its fixed timestamp makes genesis repeatable. Runtime startup,
initialization, status, logs and retirement always use the normal named Make
commands. No source/config copy or alternate worker launch is used.

Acceptance proves catch-up, idle-tip behavior, later arrivals, clean shutdown,
restart in a new process and preservation of the previous durable block/event
prefix. The generated TOML lock is ignored and removed only after its owned
input volume is retired. Tracked deployment files remain in place. Existing
resources or locks are refused before mutation; uncertainty retains private
evidence under out/deployment-acceptance/ and blocks automatic reuse. The test
never tears down SQL/RPC while the retained consumer may still be alive.

Blind Make naming workshop — 13 November 2026
---------------------------------------------
The first slice aligned all acceptance entry points under test/:
  test/deployment/acceptance/run
  test/indexer/acceptance/borrowed/run
  test/indexer/acceptance/owned/run
Borrowed acceptance keeps producer lifecycle rights external. Owned acceptance
creates and retires its fixture. Deployment acceptance uses the normal named
lifecycle with its own disposable SQL/RPC dependencies.

Three reusable gpt-6-luna readers at low reasoning effort received no repository
context and used no tools. Each first interpreted all 30 public target names
and all 13 parameter names. The coordinator compared their predictions with
the owning dispatchers, named lifecycle, staging, history and wheelhouse code.

All three identified consequential uncertainty in four names. A second blind
round interpreted these candidates and selected commands for concrete tasks:
  deployment/init          -> deployment/config/init
  deployment/database/init -> deployment/database/schema/init
  deployment/inputs/create -> deployment/inputs/stage
  history/advance          -> history/block/advance
The revised names identify configuration rather than general provisioning,
schema rather than database-server creation, staging rather than generation,
and block advancement rather than an unspecified history operation. Old names
have no aliases. No operation or resource grant was expanded.

Later rounds gave readers the proposed operator help and asked them to select
operations, order prerequisites, predict retained state and reject unsupported
requests. Work was divided across build/dependency, deployment and acceptance
scenarios. Readers selected the distinct runner roles, preserved the borrowed
producer, chose the owned lane for transactions/reorg exercises, and separated
schema initialization from external PostgreSQL provisioning. They did not infer
payment-accounting qualification or automatic production reorganization repair.
Names alone did not establish offline behavior, exact cleanup scope, immutable
image selectors or file formats; those belong in help and this contract.

Two parameter teach-backs needed follow-up. One reader initially split
DATABASE_NETWORK; another grouped WHEELHOUSE among resource names. Subsequent
value-selection checks distinguished the Engine bridge name, absolute host
wheel pool path, private DSN file path, deployment name, volume name and image
ID. A reader also requested that the indexer test's required RUNNER_IMAGE be
explicit in help. Existing parameter names were retained.

The reusable readers were reader_a, reader_b and reader_c in this Codex session.
Independent diff review found one stale example instruction, corrected before
commit. These are qualitative usability observations, not execution evidence
or a statistically independent user study: reused readers retain earlier rounds.
Both naming slices demonstrated exported-API RED then GREEN and passed all
148 host repository checks. Real Engine acceptance was not rerun for these
interface-only changes; earlier Engine results apply to the preceding revision.

Named Reader snapshots (separate consumer authority)
----------------------------------------------------

Use the same DEPLOYMENT=<name> and the same deployment.toml chain, contract,
ABI and network selections. No independent editable Reader catalog exists.
The operator derives a Reader projection using the existing catalog shape,
with database.runtime_role = conix_reader, and selects only the private
secrets/reader.dsn (0600). Existing indexer/owner credentials are never
staged, mounted or forwarded to a Reader.

  make deployment/reader/prepare DEPLOYMENT=local
  make deployment/reader/check DEPLOYMENT=local
  make deployment/reader/status DEPLOYMENT=local
  make deployment/reader/remove DEPLOYMENT=local

Preparation uses the prepared indexer image without rebuilding it, stages
the Reader catalog and selected ABI members through the same networkless
stdin-only provisioner, then atomically publishes a distinct reader.lock.toml
(image/volume; version 1). A Reader lock may not point to the writer volume.
Failed staging or lock publication does not replace the previous Reader lock;
old inputs are only retired after a new selection is published. An active
indexer does not block Reader snapshot preparation.

The catalog admits the two existing DB role names but never authorizes
writer/schema use of a conix_reader catalog. The original open_reader
continues to require actual conix_reader PostgreSQL credentials and verifies
the selected source and trusted RPC. The check uses a separate one-shot
container (no daemon) with an exact pinned image, Reader-only volume mounted
read-only, internal database/RPC bridges, no host bind, ports or broad caps.
It prints a bounded source/checkpoint result only after owned container
retirement is confirmed; failed check or cleanup retains the primary error
and reports cleanup uncertainty separately.

Status displays only immutable image/volume coordinates, never DSNs. Remove
retires only the owned Reader volume after inspecting its exact lock and
preserves the lock on unconfirmed removal. It does not retire an indexer
container, its input volume, SQL or network resources. A Reader application
may independently attach the selected volume and bridges on the same local
Engine; it owns its lifetime. Cross-host distribution and Reader HTTP service
provisioning are not part of this operator contract.

Qualify source/ABI parity, role fencing, immutable snapshot/lock behavior,
privilege grants, independent Reader/indexer lifetimes, primary failure and
cleanup uncertainty, real reader/check DB/RPC access and owned teardown.
The existing retained-deployment acceptance campaign provides the selected
rootless Engine lifecycle proof; ordinary CI alone does not.
