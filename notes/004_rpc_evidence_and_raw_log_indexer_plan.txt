Conix — RPC findings and raw-log implementation plan
=====================================================

2026-11-09 | Candidate design decision, not implemented or qualified.
Related: notes/000_architecture_guidelines.txt,
notes/001_implementation_plan.txt, notes/003_declarative_evm_indexer_design.txt.

This note records what the observed public-RPC behavior changes about the
generic Conix proposal. It narrows note 003's candidate decoded-field store
and nonindexed equality filters; those remain possible future optimizations,
not first-release requirements. It does NOT cancel the type-safety tests or
the existing durable-block/reorganization guarantees.

Provider details that affect architecture:

- Ethereum mainnet, Ethereum Sepolia, Base mainnet and Base Sepolia returned
  -32701 for the range request but returned real Transfer logs via blockHash:
  620, 109, 10 and 5 respectively. The range request covered four blocks
  across ALL emitting addresses. This does not establish that a query
  restricted to one contract/event would fail.
- BSC mainnet and testnet returned -32005 for BOTH log-query forms. Neither
  endpoint is qualified for Conix ingestion by this measurement.
- Nine blockHash log probes returned no Transfer logs in the selected sample.
  Empty is inconclusive; test against a known nonempty block before admission.
- The five failed historical eth_call probes were Ethereum mainnet, both
  BSC networks and both opBNB networks. The probe used an identity precompile
  only 4096 blocks back, not a deployed historical contract or archive depth.
- Finalized-tag acceptance and requireCanonical argument acceptance do not
  independently establish consensus, nor was a genuine reorganization tested.
- getBlockReceipts failures are not blockers: the core does not need it.

Implication: block-hash log selection and EIP-1898 reads are viable across
many no-key providers. However, correct answers from the chosen RPC remain
a trust assumption. No provider check can prove absence of omitted logs.
Do not infer this from a reported "OK" or an empty log array.

What Conix actually needs
-------------------------

1. Chain and identified block reads (eth_chainId, eth_getBlockByNumber).
2. Complete processing of logs for an explicit contract/event selection
   in one identified block (eth_getLogs with blockHash/address/topics).
3. ABI-typed read-only eth_call pinned to the SAME checkpoint when the
   consumer needs contract state.
4. Optional canonical/finalized evidence according to consumer policy.

eth_getBlockReceipts is a possible corroboration/optimization, not a
prerequisite. eth_getBalance, eth_getStorageAt, traces, signing, submission,
arbitrary JSON-RPC methods and an indexer-specific filter language are not
needed by the proposed core.

Conix currently queries PayToPlay VoucherCollected using blockHash, contract
address and topic0 (src/conix/pay_to_play.py), and viewPosition/asset using
EIP-1898. Preserve those guarantees, not necessarily their special-case
implementation. The current Chain.assert_source() bytecode-present-at-latest
check is inappropriate for historical event indexing: old logs can be
legitimate without code at the current tip. Move any code-availability
requirement to the selected historical contract call.

dapp32's existing restricted indexer proxy allows eth_chainId,
eth_blockNumber, eth_getBlockByNumber and eth_getLogs, but NOT eth_call.
Conix's view reader therefore needs either a reviewed proxy allowlist
change or a separate confined read-only RPC route. Never silently bypass
this network boundary.

Minimal event history: raw facts
--------------------------------

Operator configuration describes a single explicitly identified chain,
a fixed collection of contract addresses, complete ABI files, selected
nonanonymous events and a history origin. The ABI is the only language
describing types. No checks grammar, column grammar or [views] binding
language is justified.

Proposed durable concepts:

  source_progress — chain/genesis + immutable indexing-catalog fingerprint;
                    origin; complete checkpoint; generation/revision and
                    blocked/observed-head state.

  blocks          — contiguous block number, hash, parent hash, timestamp.
                    Includes blocks with zero selected events.

  events          — selected occurrence's block number/hash, transaction
                    hash/index, log index, emitter address, topic0..topic3
                    and the original data byte sequence.

Represent topics and data as PostgreSQL bytea; missing topics are not
zero-valued topics. Raw log metadata must be checked against the selected
block, with unique occurrence identity and deterministic chain ordering.
There can be gaps between log indices because only configured events
are retained. De-duplicate overlapping selectors by exact occurrence
identity; reject conflicting descriptions of that occurrence.

No persisted ABI-decoded uint256, amount, invoiceHash or generic JSONB fields
are necessary initially. Raw storage avoids the costly ABI -> SQL numeric/
JSON -> filter -> Python type conversion path seen in rindexer. BUT it does
not eliminate type safety: the ABI descriptor governs structural validation
during ingestion, filter encoding, on-demand decoding and view-call arguments
and results. One invalid/malformed matching log must fail the block rather
than be omitted or published as undecodable complete history.

Keep atomic publication of all configured events from ALL selected contracts
for a block, and preserve writer lock, checked basis, generation invalidation,
explicit manual repair, no RPC inside SQL transactions, and owner/runtime
privilege separation. A failed contract query must not advance the block
checkpoint using the other contracts' events.

One-block PUBLICATION does not logically require one-block ACQUISITION.
Begin with the simple blockHash path and benchmark historical catch-up.
Bounded batch/range acquisition can be considered later only if it keeps
every complete-block/checkpoint guarantee. Do not assume that because
range requests had failures for a global Transfer filter, every narrower
range request is unusable.

Queries and exact type semantics
--------------------------------

The public API is the same across PayToPlay, ERC-20 and ERC-721:

    checkpoint = await reader.checkpoint()

    page = await reader.events(
        checkpoint=checkpoint,
        contract="payment",
        event="VoucherCollected(address,uint256,address,uint256,uint256,bytes32)",
        where={"customer": customer, "channelId": channel_id},
        cursor=None,
        limit=100,
    )

    state = await reader.call(
        checkpoint=checkpoint,
        contract="payment",
        function="viewPosition(address,uint256,address)",
        arguments=(customer, channel_id, actor),
    )

    evidence = await reader.evidence(
        checkpoint=checkpoint,
        block_numbers=(100, 105),
        include_finalized=True,
    )

The where mapping supports ABI-typed equality on supported INDEXED SCALAR
arguments only. The ABI encoder builds exact 32-byte topic values; PostgreSQL
compares those bytes. Check signedness, widths and padding; reject bool as
int, float as integer, overflow, invalid addresses and fixed-byte lengths.

Indexed dynamic/array/tuple arguments are topic HASHES, not recoverable
preimages. Expose them accurately, and do not promise preimage filtering
unless its separate Solidity hashing semantics are implemented and tested.

The complete event declaration, including indexed flags, must determine
decoding. ERC-20 and ERC-721 have the same
Transfer(address,address,uint256) event signature but different indexed
layouts. Resolve against the specific emitting contract and ABI. Reject
ambiguous incompatible layouts on the same contract before startup.

Queryable event count and page completion must be about this exact
source/catalog, history generation, selected event/filter, and fixed
checkpoint. A cursor must not turn global sequence offsets into false
evidence of completeness for sparse filtered pages. Reorg-invalidated
cursors and checkpoints must fail, including same-height A->B->A.

Performance-driven indexes should match real requests, including topic2-
only and topic3-only equality. A composite index beginning with topic1
will not necessarily accelerate these. Choose after query-plan and
storage measurements, not by exposing SQL indexes as configuration.

Read-only contract calls are ABI-defined (no duplicated [views] config),
pinned to the checkpoint's block hash, and followed by generation checks.
An RPC that lacks historical state causes an explicit unavailable result;
that limitation must not stop independent raw-log ingestion.

PayToPlay consumer migration
----------------------------

VoucherCollected indexed fields:
  customer=topic1, channelId=topic2, payee=topic3.
Nonindexed fields:
  amount, voucherPaid, invoiceHash.

Current pay-to-play/src/management/cycle_evidence.py fetches deployment-wide
pages; ledger/accounting.py verifies a global collection-count sequence and
then filters by (customer, channelId). The generic reader can fetch only the
matching topics. Replace the global completeness proof with a sound
position-filtered history completeness proof. Missing earlier history
must never become "zero collections". Keep invoice and money validation
in PayToPlay when Conix stops rejecting ABI-valid but economically strange
logs. Conix must not interpret contracts as accounting policy.

Implementation gates, in order
------------------------------

1. Record raw-log/checkpoint/query contracts and a supported ABI type matrix.
   Update superseded portions of note 003/001 deliberately; do not claim
   this note alone implements their end state.

2. Implement catalog compiler and attack tests: ABI ambiguity, overloads,
   indexed layouts, duplicate/unnamed fields, dynamic indexed hashes,
   unsupported types, explicit chain/genesis/source identity.
   Reuse tests/test_abi_type_safety.py, tests/test_abi_golden_vectors.py and
   the existing typed-view tests. ERC-20 vs ERC-721 is mandatory.

3. Implement raw journal and generic block scanner with REAL PostgreSQL
   tests for multiple contracts, empty blocks, exact topic/data storage,
   deduplication, malformed logs, unknown COMMIT, restart and reorg.
   Reuse the existing concrete publication and repair machinery rather
   than introducing a second scanner hidden behind a facade.

4. Implement checkpoint/call/events/evidence on raw history: typed topic
   equality, sparse pagination, generation-bound cursors, historical calls,
   and exact decoded values. Test rejected unsupported queries as well as
   successful ones. Benchmark indexing/storage/filter plans.

5. Integrate the REAL PayToPlay accounting worker, not a mock of its output;
   signed invoice/voucher -> collection -> indexing -> payment cycle ->
   restart -> reorg/reconciliation. Financial safeguards remain in the
   consumer. Run independent actual Solidity/Anvil ERC-20 and ERC-721
   scenarios through the very same installed generic Conix package.

6. Independently improve dapp32's RPC qualification: request logs for a
   KNOWN nonempty receipt by exact emitting address, topic0 and blockHash;
   test real historical deployed contract state and a range of history
   depths. Resolve the BSC -32005 and testnet empty-log uncertainties.
   This can proceed alongside generic core work; provider success is
   not proof of event completeness.

Explicitly deferred: nonindexed-field predicates, generic derived tables,
SQL or view grammars, GraphQL/HTTP, streaming/subscriptions, bulk performance
features without measurement, autonomous repair and speculative caching.

Release-blocking invariant: a checkpoint means that all configured sources
were processed through that exact block under a declared RPC trust boundary.
No type conversion, dropped log, partially published block, incorrect
filtered completion, stale generation or lost financial safeguard can be
accepted as a qualified implementation.
